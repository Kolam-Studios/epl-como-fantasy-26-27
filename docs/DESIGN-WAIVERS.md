# Design proposal: the waiver era

> Status: RATIFIED (owner sign-off, Aug 2026); the waiver-era build follows this document as the spec of record. This document specifies the platform's move from the completed live auction into the monthly blind-bid waiver era, plus the fixes to shared surfaces (squads, ledger, console) that the waiver screens depend on. Nothing here is a migration or production code. The locked visual system in `docs/VISUAL-DESIGN.md` applies to every screen below; this document only adds product behavior and flags the small set of genuinely new components.
>
> House rules apply: placeholder names only (Manager A through Manager H). Real rosters live only in gitignored local config. Interactive HTML mockups for every screen (desktop and mobile) accompany this proposal outside the repo.

## 0. Open questions

Decisions the owners still need to make. The design below picks a default for each so the build is not blocked, but each default should be confirmed.

1. **RESOLVED (owner ruling, Aug 2026): trades are always allowed.** Every phase gets a Trades sub-tab: the live trade log for the current period, frozen for archived periods. Design in section 2.3; engine interactions in section 4.4.
2. **Bid 2 date** (owners' poll pending, 2nd or 3rd week of January). The phase tab ships as locked with "date TBD" until confirmed.
3. **Token assignment.** The scheme is one memorable word per manager, static for the season, generated by the Commissioners. The examples in this document (NORWAY, BRUNO) are placeholders; real assignments never enter the repo.
4. **RESOLVED (owner ruling, Aug 2026): the sat-out manager is out for the season; the league plays with seven.** No waiver re-entry rule is needed. Sat-out managers never appear in the waiver form's manager dropdown or the token history lookup; their frozen $3,000 row stays in every archive as the record.
5. **RESOLVED (owner ruling, Aug 2026): valuations return at Bid 2 only.** No new Claude valuations are generated during the waiver months. Value and verdict columns on waiver-era ledgers keep showing the values from the most recent bid round as the historical record; fresh valuations (retuned via the post-mortem work) arrive with Bid 2.
6. **PART-RESOLVED (owner ruling, Aug 2026): waiver results WILL be revealed, not quietly published.** The reveal format (board-style takeover, a scheduled reveal night, or something else) is deliberately left open for a later discussion; the engine's output (the ordered outcome log plus the seed) is already shaped to be replayed dramatically, bid by bid, whatever format the owners pick.
7. **Charts scope per waiver period.** The archive mockup proposes: spend by manager, spend by position, price-vs-value tiles, awards. Confirm which of these matter monthly versus only at the rebid.
8. **Retention of superseded submissions.** The token history page shows all past versions of a manager's form. Confirm indefinite retention is wanted (it is the audit trail; default yes).
9. **Absent owner input.** One owner has not yet weighed in on any waiver-era decision; several items here (values, tiers, history data) assume that input still arrives.

## 1. Overview

The auction is done; the season now runs in monthly periods. All submissions are due the last Saturday of the month at 5:00pm AEST:

| Period | Cutoff | Type |
|---|---|---|
| Bid 1 COMO2526 | closed 2 Aug 2026 | live auction (becomes archived period 1) |
| Waiver 1 | Sat 26 Sep | blind-bid waiver |
| Waiver 2 | Sat 31 Oct | blind-bid waiver |
| Waiver 3 | Sat 28 Nov | blind-bid waiver |
| December | skipped | rolls into the rebid |
| Bid 2 | Jan, date TBD | live auction |
| Waiver 4 | Sat 27 or 28 Feb | blind-bid waiver |
| Waiver 5 | Sat 27 Mar | blind-bid waiver |

Three product shifts fall out of this:

1. **The site becomes period-centric.** The top-level navigation is the season's phases; each phase carries the same five sub-views (budget, squads, ledger, trades, charts and analysis). The current phase is live; future phases are locked; past phases are frozen archives.
2. **Managers become writers.** The auction app had one writer (the commissioner console). The waiver form is a manager-facing write path, gated by a per-manager token. Tokens are the only credential; there are no accounts.
3. **Money only ever goes down.** Consistent with the auction-era trade money model, spend is monotonic: waiver wins subtract the winning bid from the wallet, and drops refund nothing. Remaining budget is still derived at read time, never stored.

## 2. Information architecture

### 2.1 Navigation (mockup A)

Two-level navigation replaces the current flat five-tab room nav:

- **Phase rail** (top level): Bid 1 COMO2526, Waiver 1 Sep, Waiver 2 Oct, Waiver 3 Nov, Bid 2 Jan, Waiver 4 Feb, Waiver 5 Mar, then Rules, then History. Calendar order, utilities at the end. The rail scrolls horizontally when needed; tabs never shrink.
- **Sub-tabs** (per phase): Budget, Squads, Ledger, Trades, Charts + Analysis.

Phase states:

| State | Tab treatment | Landing content |
|---|---|---|
| current | green live dot | the live surface: waiver form entry point, countdown, current budgets |
| future | dimmed, padlock | "Waiver period locked" stub with its open and cutoff dates |
| past | plain | the frozen archived-period summary (section 2.2) |

The site root always resolves to the current phase. During a live rebid the current phase is the auction board itself; the board, reveal and console routes are unchanged by this redesign.

Mobile: the same phase rail becomes swipeable with the active tab auto-scrolled into view; sub-tabs stretch to equal quarters. This is a genuinely new pattern (the current fixed phone nav cannot hold nine-plus tabs) and is flagged in section 6.

### 2.2 Period lifecycle and archiving (mockup D)

A period moves: `locked -> open -> resolving -> closed`.

At close, the period freezes into an archive: a summary page (who won what, transfers), the ledger as it stood, all squads, all budgets, that period's trades, charts, and awards. Archived pages are snapshots, not live queries; nothing on them ever recomputes. The August auction is retro-fitted as the first archived period ("Bid 1 COMO2526"), satisfying the existing requirement that the auction record is preserved permanently.

### 2.3 Trades in the waiver era

Trades stay open all season (owner ruling). The mechanics are unchanged from auction night: two-sided player and/or cash moves, entered by the Commissioners in the console, validated with the same guardrails (no negative budgets, position quotas, squads at 15), audited, salaries traveling with players and no refunds on either side.

What changes is bookkeeping and presentation:

- Every trade is stamped with the period it happened in. The current phase's Trades sub-tab is the live log of that period's trades; an archived phase's Trades sub-tab is frozen with everything else.
- The console trade form is available whenever the season is running, with one exception: **trades pause while a period is resolving**, from the waiver cutoff (Sat 5:00pm AEST) until the results publish. The engine must run on stable budgets and rosters; a trade slipping in between cutoff and resolution would change the inputs after the forms were final. The console shows the reason and the reopen time.
- Players won at a waiver are tradeable as soon as the period closes.

## 3. Screens

Each screen has an interactive mockup rendered against the real design tokens, in desktop and mobile forms. Summaries here; the mockups are the visual truth.

### A. Phase navigation (mockup A)

Covered in section 2.1. Components: new `phase-rail` and `sub-rail` patterns derived from the existing room-nav tab (same type, same bronze active underline); new state chips for live, locked and archived.

### B. Waiver blind-bid form (mockup B)

The headline build. A four-step form, one card, with a progress rail:

1. **Who you are.** Token input plus manager dropdown. The pair must match (server-side check); mismatch is a plain red inline error. On match, the manager's remaining budget and squad load. If a form is already on file for this period, it loads pre-filled with a banner ("submitted Tue 9:41pm; edit and resubmit to replace it").
2. **Nominate drops.** The full 15-player squad renders grouped by position, each row a keep-or-drop toggle. Dropped players get a priority order (the manager's stated drop order). A live summary translates nominations into rights: "2 FWD and 1 MID nominated: you can win at most 2 forwards and 1 midfielder."
3. **Blind bids.** Any number of bid rows; each row is a free-agent search (accent-insensitive, same folding rule as the console search in mockup H) plus an amount. Validation: whole dollars, minimum $1, each bid capped at the manager's full remaining budget. A bid on a position with no nominated drop shows a warning (it can never win) but is not blocked. Bids do not reserve funds; you only pay for wins.
4. **Review and submit.** Drops in priority order, bids high to low with their position match restated, then submit. The confirmation states the resubmission rule: any number of forms may be submitted; the latest one before the cutoff is the one that counts.

Nobody can see anyone's bids or drops (including their own room-mates') until the round resolves. Drops are invisible to other managers even after submission; they surface only in the resolution results.

Bid-cap note: the waiver cap is the manager's full remaining wallet, with no per-slot reserve. The auction's max-bid rule reserved an opening bid per open slot because squads were incomplete; waiver squads are always full and every win is a one-for-one same-position swap, so the squad stays valid without a reserve.

Server-side validation at submission: token matches manager; manager is active this period; every dropped player is currently owned by the manager; every bid target is a free agent; amounts within cap; at most one bid per player per form; submission timestamp before cutoff.

### C. Token history page (mockup C)

Enter a token, see your own record: the saved live form for the current period (with an edit path back into mockup B), and all past submissions, period by period, including superseded versions with timestamps. Three deliberate non-account properties: the token is the only key (no email, no recovery flow; lost tokens are reissued by the Commissioners); lookups never confirm whether a token exists (wrong input reads "no submissions found", not "bad token"); nothing personal is stored beyond the manager mapping that already exists in league config.

### D. Archived-period summary (mockup D)

The frozen record of a closed period, using the four sub-tabs: Budget (final wallets), Squads (final 15s), Ledger (as it stood at close, with the full filter system from screen E), Charts + Analysis (spend by manager, spend by position, price-vs-value tiles, and the period's awards). For waiver periods the summary leads with the transfer record: who won which player at what price and who they dropped. The auction is archived in exactly this shape as period 1.

### E. Ledger filters (mockup E)

Fixes the auction-night gap where filtering existed only on the phone. One filter model shared by desktop and phone; only the layout differs:

- Status: all, sold, unsold (single-select).
- Position: GK, DEF, MID, FWD (multi-select chips).
- Club: multi-select popover with search (sheet-style panel on phone).
- Active filters render as removable pills with a clear-all; a live count shows "31 of 40 players".
- Price and value columns sort on click.

This component is reused by every archived period's ledger and by the waiver form's free-agent picker.

### F. Squads view, fixed (mockup F)

Fixes two auction-night bugs: desktop cards capped at 5 players, and the TV squads screen rendering blank. The fix is one squad-card component that always renders all 15 players, grouped by position, serving three containers: the desktop two-column grid, the phone single column, and the TV's fixed 1600x900 canvas (4x2 grid of cells). The TV canvas keeps the documented scale guard: when the measured container width is zero (backgrounded tab), leave the scale unset and retry on the next animation frame; never apply scale(0). Archived periods freeze this same layout.

### G. COMO history (mockup G)

The all-time archive at the end of the nav: an accordion of seasons, COMO2526 open at the top, then prior seasons newest first. Each past season card: champion, runner-up, wooden spoon, a memorable stat, and award chips. The design tolerates sparse data with muted "not recorded" fields, because the owners are still recovering old records. COMO2526 links into the in-app period archives; older seasons are flat records.

### H. Console additions (mockup H, annotated)

Four operator improvements for the January rebid, in the console's dark skin:

1. **Build queue button.** The morning `buildQueue` script becomes a confirm-gated console button ("Build queue + open lot 1"), disabled once any sale exists.
2. **Sit-out toggle.** A per-manager tick that greys the manager everywhere (console picker, board budget strip), skips them in the phase-2 nomination rotation, and hides them from the waiver form's manager dropdown. Untick to rejoin instantly.
3. **Accent-insensitive search.** Nomination search folds diacritics on both sides, so typing plain ASCII finds accented names. Display always keeps the true spelling.
4. **Skip-aware undo.** Replaces the single "undo last sale" with a recent-lots list where each sold lot has its own undo and each no-bid lot can be reopened, so correcting one sale never walks back the no-bid lots recorded after it.

## 4. The waiver engine

### 4.1 Definitions

- **Free agent:** a player owned by nobody: never sold at auction, or dropped in a previously closed period. Players dropped in the current round do not become biddable until the next period.
- **Drop slot:** one nominated drop of a given position grants the right to win one player of that same position. Slots are counted per position, not pooled.
- **Effective form:** a manager's latest submission before the cutoff. Everything earlier is superseded (kept for history, ignored by the engine).
- **Start-of-round remaining:** the manager's remaining budget at the moment resolution begins. Used for the tie-break so that tie outcomes never depend on processing order.

### 4.2 Resolution algorithm

At the cutoff the period enters `resolving` and the engine runs once, deterministically:

```
INPUT: effective form per active manager
       (drops with priority order, bids with amounts)
       start-of-round remaining budget per manager
       a random seed, fixed and published with the results

1. Collect every bid from every effective form into one list.
2. Sort the list:
     a. amount, high to low
     b. ties on the same player: larger bid as a proportion of that
        manager's start-of-round remaining budget wins (equivalently,
        the smaller purse wins); if still equal, seed order
     c. ties within one manager (equal amounts, different players):
        the order the bids appear on their form
     d. all other equal-amount pairs contend for nothing; seed order,
        outcome-neutral
3. Walk the sorted list. For each bid (manager m, player p, amount a):
     AWARD the bid only if ALL hold:
       i.   p has not already been awarded this round
       ii.  m's working budget >= a
       iii. m has an unused drop slot for p's position
     On AWARD:
       - m pays a (working budget -= a)
       - consume one drop slot for p's position
       - release m's highest-priority not-yet-released nominated
         drop of that position
     Otherwise SKIP the bid: no funds are spent, no slot is consumed,
     and p remains available to lower bids from other managers.
     Record every outcome with its reason:
       won | player_taken | skipped_funds | skipped_position |
       skipped_capacity | lost_tie
4. Publish: awards (player, winner, price, released drop), the full
   outcome log, and the seed. Apply the moves. Close the period and
   freeze its archive. Open the next period.
```

Publication is a reveal, not a quiet page update (owner ruling; format to be designed separately). The ordered outcome log is the script for it: the resolution can be replayed bid by bid, highest first, exactly as the engine walked it.

Consequences worth stating plainly:

- A manager wins at most the number of players they nominated to drop, position by position. Win rights are consumed as awards happen, highest bid first.
- A skipped bid never removes the player: if the top bid on a player is skipped (no slot, no funds), the next-highest bid on that same player is evaluated normally. Players "return to the pool for others" automatically because the walk continues.
- Drops execute only against wins. Nominated players whose slots were never consumed stay on the squad, untouched.
- No refund on drops; the released player's salary simply leaves with them. Spend only rises; remaining only falls.
- Funds are checked against the working budget, so early wins can price a manager out of their own later bids; those later bids skip without spending.
- Any manager with no effective form simply sits the period out.

### 4.3 Worked example, four managers

Squads are full (15/15). Start-of-round remaining: Manager A $120, Manager B $95, Manager C $260, Manager D $40.

Effective forms (players are labeled by position for hand-checking; FW1 to FW4, MF1, DF1, GK1 are free agents; FW-a, MF-b etc. are owned players nominated as drops):

| Manager | Drops nominated (priority order) | Bids |
|---|---|---|
| A | FW-a, FW-b, MF-a | FW1 $60, FW2 $45, FW3 $30, MF1 $25, FW4 $20 |
| B | FW-c | FW1 $60, MF1 $40 |
| C | MF-b, DF-a | DF1 $80, MF1 $50, FW2 $50 |
| D | FW-d, GK-a | FW1 $38, FW4 $30, GK1 $25, FW3 $12 |

So the drop slots are: A: 2 FWD + 1 MID. B: 1 FWD. C: 1 MID + 1 DEF. D: 1 FWD + 1 GK.

The single sorted pass:

| # | Bid | Check | Outcome | Working budgets after |
|---|---|---|---|---|
| 1 | C bids $80 on DF1 | DEF slot free, $260 covers it | **C wins DF1 for $80**, drops DF-a | C $180 |
| 2 | A and B both bid $60 on FW1 | tie: A's $60 is 50.0% of $120, B's $60 is 63.2% of $95 | **B wins the tie and FW1 for $60**, drops FW-c; A's bid: lost_tie | B $35 |
| 3 | C bids $50 on MF1 | MID slot free, $180 covers it | **C wins MF1 for $50**, drops MF-b | C $130 |
| 4 | C bids $50 on FW2 | C nominated no FWD drop | SKIP, skipped_position, no funds spent, FW2 stays available | C $130 |
| 5 | A bids $45 on FW2 | FWD slots 2 free, $120 covers it | **A wins FW2 for $45**, drops FW-a (priority 1) | A $75 |
| 6 | B bids $40 on MF1 | MF1 already awarded | dead, player_taken | B $35 |
| 7 | D bids $38 on FW1 | FW1 already awarded | dead, player_taken | D $40 |
| 8 | A bids $30 on FW3 | 1 FWD slot left, $75 covers it | **A wins FW3 for $30**, drops FW-b (priority 2) | A $45 |
| 9 | D bids $30 on FW4 | FWD slot free, $40 covers it | **D wins FW4 for $30**, drops FW-d | D $10 |
| 10 | D bids $25 on GK1 | $10 left, cannot cover $25 | SKIP, skipped_funds; GK1 goes unawarded and stays in the pool | D $10 |
| 11 | A bids $25 on MF1 | already awarded | dead, player_taken | A $45 |
| 12 | A bids $20 on FW4 | already awarded (and A has no FWD slot left anyway) | dead, player_taken | A $45 |
| 13 | D bids $12 on FW3 | already awarded | dead, player_taken | D $10 |

Final state to sanity-check by hand:

| Manager | Won | Paid | Dropped | Remaining | Notes |
|---|---|---|---|---|---|
| A | FW2, FW3 | $75 | FW-a, FW-b | $45 | MF-a was nominated but never released: no MID win |
| B | FW1 | $60 | FW-c | $35 | won the tie despite equal money, smaller purse |
| C | DF1, MF1 | $130 | DF-a, MF-b | $130 | its $50 FW2 bid could never win: no FWD drop |
| D | FW4 | $30 | FW-d | $10 | GK1 bid priced out by its own FW4 win; GK-a retained |

Every rule appears at least once: the proportional tie-break (row 2), position matching (row 4), a lower bid taking a player after a higher bid skipped (rows 4 to 5), per-position capacity (row 12), funds exhaustion without spend (row 10), unexecuted drops retained (A's MF-a, D's GK-a), and squads remaining exactly 15/15 with position quotas intact throughout.

### 4.4 Trades and the engine

Because trades run all season (section 2.3), the state a form was written against can change before the cutoff. The engine handles this without special cases, by re-validating everything against the true state at resolution time:

- **Funds:** the bid cap was checked at submission, but the working budget at resolution is what counts. A manager who traded cash away after submitting may find later bids skipped for funds; one who received cash still cannot exceed a bid amount as written.
- **Drops:** a nominated drop must still be owned by the manager when the engine runs. A nominated player who was traded away in the meantime is simply not a valid drop any more; that slot evaporates and bids that depended on it skip for position. Drops are re-validated per position at resolution, never trusted from the form.
- **Free agents:** the bid target must still be a free agent at resolution (trades cannot create this conflict today, since trades move owned players, but the check is cheap and future-proof).
- **The blackout:** trades pause from cutoff to publication, so within a single resolution run the state cannot move underneath the walk.

The waiver form warns on submission if a manager's plans are fragile (for example a single nominated drop backing several bids), but it never blocks on the possibility of a future trade.

## 5. Data-model delta (proposal, not a migration)

Additive only, consistent with the existing guarded-migration pattern. Live money numbers stay derived; archives are deliberate snapshots, extending the existing season_recap precedent.

```
periods             id, season, kind (rebid|waiver), label, seq,
                    opens_at, cutoff_at,
                    status (locked|open|resolving|closed)
                    -- formalizes the existing sales.stage / trades.stage
                    -- strings; app_state gains current_period_id; trades
                    -- gain a period_id stamp (or keep stage = period label)
                    -- so each phase's Trades sub-tab is a simple filter

manager_tokens      manager_id PK -> managers, token_hash, created_at,
                    rotated_at
                    -- one memorable word per manager, compared
                    -- case-insensitively, hashed at rest, never in any
                    -- payload; reissue = rotate the hash

waiver_submissions  id, period_id -> periods, manager_id -> managers,
                    submitted_at
                    -- every submission is kept; the effective form is
                    -- the latest submitted_at before the cutoff

waiver_drops        id, submission_id -> waiver_submissions,
                    player_id -> players, priority
                    -- position derives from players; UNIQUE
                    -- (submission_id, player_id)

waiver_bids         id, submission_id -> waiver_submissions,
                    player_id -> players, amount (> 0)
                    -- UNIQUE (submission_id, player_id); amount <=
                    -- remaining is validated at submit AND re-checked
                    -- at resolution

waiver_results      id, period_id UNIQUE -> periods, seed, resolved_at
waiver_outcomes     id, result_id -> waiver_results, sequence,
                    bid reference (manager_id, player_id, amount),
                    outcome (won|player_taken|skipped_funds|
                             skipped_position|skipped_capacity|lost_tie),
                    price, dropped_player_id (nullable)
                    -- the full processing log: powers the period
                    -- summary, the token history page, and disputes

drops               id, period_id -> periods, manager_id -> managers,
                    player_id -> players, created_at
                    -- executed drops only; ownership resolution becomes
                    -- sales JOIN trade movements MINUS drops

period_snapshots    period_id PK -> periods, payload (jsonb), frozen_at
                    -- the frozen archive: budgets, squads, ledger rows,
                    -- chart aggregates, awards; written once at close;
                    -- the August auction is backfilled as the first row
```

Applying a resolution = one transaction: insert waiver_results and waiver_outcomes, insert a sales row per win (stage = the period label, preserving the exclusive-ownership constraint), insert drops rows per released player, write the audit rows, close the period, freeze period_snapshots, open the next period, bump the state version.

Derived-money update: `spend(m)` becomes auction buys + net trade cash + waiver wins, for players currently owned or since dropped (no refunds). Ownership view subtracts drops. Nothing stored.

Write-path note: waiver submission is the first non-commissioner write. It is gated by the manager token (its own header, not COMMISSIONER_TOKEN), validates everything server-side, and writes an audit row like every other mutation. Resolution itself is a commissioner-gated action.

## 6. Design-system notes

Reused as-is: tokens, type scale, cards, pills, chips, tables, position markers, state tints, the console dark skin, the TV canvas mechanics (including the zero-width scale guard).

Genuinely new, proposed in the mockups and flagged for review:

1. **Two-level phase navigation** (desktop rail + sub-rail; swipeable phone rail). The current five-tab fixed nav cannot hold the season. Same type and active-underline language as the existing tabs.
2. **Form primitives.** Multi-step progress rail, keep-or-drop toggle rows, priority reordering, repeatable bid rows with inline validation, and a match-confirmation state. All are composed from existing tokens (hairlines, pills, tints); nothing introduces a new color.
3. **Filter system** (screen E): multi-select chip groups, a club popover with search, removable active-filter pills. Shared desktop and phone.
4. **Simple CSS bar charts and stat tiles** for the charts sub-tab (screen D). Neutral ink bars; semantic color only on money verdicts, per the system's rules.
5. **State chips** for live, locked and archived phases, built from existing tints plus muted grey; no new palette entries.
